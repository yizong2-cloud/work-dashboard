# 任务上下文库（KNOWLEDGE_BASE）

> **用途**：帮助 Agent 在分析飞书聊天记录时，正确识别/合并任务，避免把「同一个任务在不同群里的讨论」误判成多个任务；同时记录飞书之外的信息（面聊、口头确认、领导指示）。
>
> **维护规则**：
> 1. 每次更新看板前先读本文件；分析出新的任务合并依据、口头确认、依赖关系时，**同步追加**，保持持续累积。
> 2. **新事实先写入「待确认区」**（第七节），用户确认后再移入「已确认事实」——避免把一次分析误判直接固化为永久事实。
> 3. 每条事实标注 `时间 | 来源`；来源标注：**用户口头**（用户当面/对话确认，最可信）、**聊天**（飞书/Codex/DSH 记录推断）、**分析推测**（Agent 推断，需谨慎）。

## 四、任务合并 / 拆分判定规则

1. **先查本表**：新聊天里出现的任务描述，先对照「别名映射」找已有任务，命中则不新建。
2. **同一产品 + 同一功能**的讨论（即使在不同群）→ 合并为一个任务，把新信息追加到该任务时间线。
3. **不同产品线**即使名字相似（如 peace sdk vs jigsaw-cy sdk）→ 不合并。
4. **拿不准**：宁可先不动，把疑似合并点记录下来问用户。
5. 分析完成后，把本次发现的新别名、新事实追加到本文件「一、二」节。

## 五、看板数据注意事项

- 任务 `created_by`：网页端记「本人」，Agent CLI 记「agent」，批量导入记「分析导入」。
- 时间线（`task_updates`）是 Leader 理解进度的核心：每次更新都要带说明，排期调整要带原因。
- 看板数据直接写 Supabase（本地 `.env` 已配 service_role key），**无需重新部署**，刷新页面即生效。
