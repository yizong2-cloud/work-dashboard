# 个人工作进度看板方案

## 1. 项目背景

Leader 反馈，目前无法方便、持续地了解我的工作排期和需求进度，例如：

- 当前正在处理哪些需求或任务
- 每个任务目前进行到什么程度
- 任务何时开始、预计何时结束
- 中途是否插入了临时任务
- 是否遇到阻塞、方案变更或其他影响排期的情况
- 为什么某项任务的预计完成时间发生变化

因此计划开发一个**个人工作进度看板**，用于持续维护和展示个人任务状态。

该看板主要面向两类使用者：

1. **本人**：负责新增任务、更新进度、调整排期、记录临时情况。
2. **Leader**：主要负责查看，能够随时掌握当前工作状态和任务变化。

---

## 2. 核心目标

这个项目不是做一个完整的 Jira / 项目管理平台，而是做一个轻量、低维护成本的个人工作透明化工具。

Leader 打开页面后，应当能够在很短时间内回答以下问题：

1. 你现在主要在做什么？
2. 当前有哪些进行中的任务？
3. 每个任务预计什么时候完成？
4. 当前进度是多少？
5. 最近发生了什么变化？
6. 是否有临时插入的新任务？
7. 是否存在阻塞、延期或排期调整？
8. 接下来准备做什么？

## 3. 技术方案

### 3.1 推荐架构

第一版推荐使用：

- 前端：React + Vite
- 静态托管：GitHub Pages
- 数据库：Supabase PostgreSQL
- 用户认证：Supabase Auth
- 数据访问：Supabase SDK / API
- 权限控制：Supabase Row Level Security（RLS）

整体结构：

```text
浏览器
  │
  ▼
GitHub Pages
React / Vite 前端
  │
  │ Supabase SDK / HTTPS API
  ▼
Supabase
├── PostgreSQL 数据库
├── Auth
└── RLS 权限控制
```

不需要单独租赁 VPS 或传统服务器。

---

## 4. 为什么 GitHub Pages 可以满足需求

GitHub Pages 本身只能托管静态网页，不能直接运行 Node.js、Java、Python 等服务端程序。

但“静态网页”并不代表网页中的数据必须是静态的。

React 页面仍然可以通过 JavaScript 调用 Supabase API：

```text
用户打开网页
    ↓
GitHub Pages 返回前端代码
    ↓
React 启动
    ↓
从 Supabase 查询任务
    ↓
显示最新数据
```

新增任务时：

```text
填写任务
    ↓
点击保存
    ↓
浏览器调用 Supabase
    ↓
数据写入 PostgreSQL
```

因此更新任务时：

- 不需要修改 GitHub 仓库
- 不需要重新 Git Push
- 不需要重新构建
- 不需要重新部署网页

只修改数据库数据即可。

## 5. 成本

对于本项目预计的使用规模，第一版可以按 **0 元/月** 的目标实施。

预计使用：

- GitHub Pages：免费
- Supabase Free Plan：免费
- github.io 默认域名：免费
- HTTPS：免费
- Supabase Auth：免费额度内使用

本项目预计只有本人和 Leader 等极少数用户，数据也主要是文字，因此数据库和访问量都非常低。

暂时没有必要：

- 租赁 VPS
- 自己部署 PostgreSQL
- 自己维护后端服务
- 自己维护 HTTPS
- 自己做服务器监控和运维

后续如使用规模明显扩大，再评估升级即可。

## 6. 用户与权限

### 6.1 管理员

本人为管理员。

权限：

- 查看所有任务
- 创建任务
- 修改任务
- 删除任务
- 修改任务进度
- 修改排期
- 标记任务完成
- 添加任务进展
- 添加阻塞说明
- 记录临时插入任务
- 调整预计完成时间

---

### 6.2 Leader

Leader 默认作为只读用户。

权限：

- 查看任务
- 查看任务详情
- 查看进度
- 查看排期
- 查看更新记录
- 查看任务变更原因

默认不允许：

- 创建任务
- 修改任务
- 删除任务

第一版可以只做：

```text
Admin：读 / 写
Leader：只读
```

不需要开发复杂的 RBAC 权限系统。

## 7. 安全要求

### 7.1 禁止将管理员密钥写入前端

绝对不能在 GitHub Pages 前端代码中暴露：

```text
Supabase service_role key
数据库管理员密码
其他拥有服务端管理员权限的密钥
```

因为前端代码对访问者是可见的。

---

### 7.2 推荐方案

前端只使用 Supabase 允许公开使用的客户端 Key，并通过：

```text
Supabase Auth
+
Row Level Security（RLS）
```

控制数据库权限。

示例：

```text
本人账号：
SELECT
INSERT
UPDATE
DELETE

Leader：
SELECT
```

数据库本身负责权限校验，而不能单纯依赖前端隐藏按钮。

## 8. MVP 页面设计

第一版尽量简单。

核心原则：

> Leader 打开首页后，最好 5 秒内知道“现在在做什么、做到哪、什么时候结束”。

## 9. 首页

首页建议包含以下区域。

### 9.1 当前状态

页面顶部突出显示当前最主要的工作。

示例：

```text
当前正在开发

宁静拼图主题系统

进度：65%
开始：8 月 15 日
预计完成：8 月 18 日

最新进展：
主题选择页面已经完成，
正在接入主题解锁逻辑。
```

---

### 9.2 进行中的任务

卡片形式展示：

```text
宁静拼图主题系统

█████████████░░░░░ 65%

开始：8/15
预计结束：8/18

最新：
完成主题选择页面，
正在接入主题解锁逻辑。
```

建议至少显示：

- 任务名称
- 当前状态
- 当前进度
- 开始日期
- 预计结束日期
- 最新进展
- 是否阻塞

---

### 9.3 临时任务

专门展示临时插入的工作。

例如：

```text
线上 Android Crash 修复

状态：已完成
插入时间：8/16
完成时间：8/16

影响：
原“主题系统”任务暂停约 3 小时。
```

这个区域非常重要，因为它可以解释为什么原有任务进度或排期发生变化。

---

### 9.4 接下来

展示待开始任务，例如：

```text
8/19  拼图完成页面改版
8/20  BGM 切换功能
8/21  新用户引导优化
```

Leader 可以提前了解后续排期。

## 10. 任务状态

建议第一版只设置少量状态：

```text
planned       待开始
in_progress   进行中
blocked       阻塞
paused        暂停
completed     已完成
cancelled     已取消
```

不要一开始设计过多状态。

## 13. tasks 表

建议字段：

```text
id
title
description
status
priority

progress

start_date
expected_end_date
actual_end_date

current_status
block_reason

is_interrupt_task

created_at
updated_at
```

字段说明：

### id

任务唯一 ID。

### title

任务名称。

### description

任务详细说明。

### status

当前任务状态。

### priority

任务优先级。

### progress

0～100 的整数。

### start_date

实际或计划开始日期。

### expected_end_date

预计结束日期。

### actual_end_date

实际完成日期。

### current_status

一句话描述当前最新状态，例如：

```text
UI 已完成，目前正在接入后端接口。
```

### block_reason

如果任务处于 blocked 状态，记录阻塞原因。

### is_interrupt_task

标记是否为临时插入任务。

### created_at

创建时间。

### updated_at

最后修改时间。

## 14. task_updates 表

任务进展不要只覆盖成“最新状态”。

应该保留完整历史记录。

建议字段：

```text
id
task_id

type
content

old_expected_end_date
new_expected_end_date

created_at
created_by
```

---

## 15. 更新类型

type 可以包含：

```text
progress
status_change
schedule_change
blocked
unblocked
interrupt
note
completed
```

例如：

```text
8/16 10:20
[progress]
完成页面 UI。

8/16 14:30
[interrupt]
临时收到线上 Crash 修复任务，
原任务暂时暂停。

8/16 17:40
[progress]
Crash 修复完成，恢复原任务。

8/17 11:00
[schedule_change]
接口方案发生调整，
预计完成时间由 8/18 调整为 8/19。
```

---

## 16. 为什么必须保留任务时间线

对于 Leader 来说：

```text
进度：60%
```

的信息价值有限。

真正重要的是：

```text
为什么目前只有 60%？
```

因此每个任务应该提供一个 Timeline。

Leader 点击任务后，可以看到：

```text
8/15
任务创建并开始开发

8/16 10:20
页面 UI 完成

8/16 14:30
临时插入线上 Crash 修复

8/16 17:40
Crash 修复完成，继续开发

8/17 11:00
接口方案调整

8/17 11:10
预计完成日期：
8/18 → 8/19
```

这样不仅能看到结果，也能看到任务过程。

```text

预计开始

优先级
```

---

### 快速更新任务

应该尽量降低更新成本。

例如任务卡片可以直接提供：

```text

```

避免每次更新都进入非常复杂的编辑页面。

---

## 19. 一个重要的产品原则

这个看板是否能够长期使用，关键不在功能数量，而在：

> 更新一次任务需要多少操作。

如果每次更新都需要：

```text
进入后台
打开页面
找任务
编辑十几个字段
保存
```

很容易坚持几天之后就不维护。

因此第一版应该尽可能让：

```text
更新一个任务
```

在几十秒以内完成。

```text

React + Vite

GitHub Pages

Backend / Database
Supabase

Supabase Auth

Authorization
```

采用该方案的主要原因：

1. 基本可以 0 成本运行。

## 30. 给后续开发 Agent 的任务说明

请基于本文档继续完成该个人工作进度看板。

优先原则：

1. **先完成能实际使用的 MVP。**
2. 不要过度设计。
3. 管理员更新任务必须足够方便。
4. Leader 首页必须能快速理解当前工作状态。
5. 必须保留任务更新历史，而不仅仅是保存最新状态。
6. 所有数据修改应直接写入 Supabase，不依赖重新部署。
7. 权限必须由 Supabase Auth + RLS 控制。
8. 禁止将 service_role key 等管理员密钥暴露在浏览器前端。
9. 第一版优先保证桌面和手机均可正常查看。
10. 如遇到本文档未定义的小型产品细节，可以优先采用简单、易维护的实现，不必扩大产品范围。

如果需要继续推进，建议开发顺序为：

```text
1. 初始化 React + Vite
2. 创建 Supabase 项目
3. 设计数据库表
4. 配置 Auth
5. 配置 RLS
6. 完成任务 CRUD
7. 完成 task_updates
8. 完成 Dashboard
9. 完成 Task Detail + Timeline
10. 完成管理员快速更新
11. 完成移动端适配
12. 部署 GitHub Pages
13. 进行权限与安全检查
```
